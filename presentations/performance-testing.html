🎯 What is Performance Testing?

Performance testing validates how a system behaves under expected and peak load conditions — before real users encounter problems.

🏋️ Load Testing

Simulate expected concurrent users — verify the app handles normal traffic without degradation.

💥 Stress Testing

Push beyond normal limits — find the breaking point and observe how the system recovers.

🌅 Spike Testing

Sudden burst of users — validate the system's reaction to sudden traffic surges.

⏱️ Endurance Testing

Sustained load over time — detect memory leaks and resource exhaustion.

Our focus: Load testing the OrangeHRM login flow — the most critical and highest-traffic endpoint in the application.

📋 Login Test Plan — Step by Step

The login.jmx plan mirrors the smoke test exactly — same flow, same assertions, but executed by concurrent virtual users via HTTP.

  • 1
    GET /web/index.php/auth/login
    Load the login page — measures initial page load time and static asset delivery.
  • 2
    POST /web/index.php/auth/validateCredentials
    Submit credentials (Admin / admin123) — the most critical endpoint; measures auth server response time under load.
  • 3
    GET /web/index.php/dashboard/index
    Verify the dashboard loads post-login — confirms session is valid and the app serves authenticated content correctly.
  • 4
    GET /web/index.php/auth/logout
    Clean logout — ensures no session leak between iterations; resets state for the next loop.
Each virtual user runs all 4 steps in sequence, independently and concurrently with other users.

⚙️ Load Configuration Parameters

ParameterFlagDefault
Virtual Users-Jthreads=N1
Iterations-Jloops=N1
Ramp-up (sec)-Jramp_up=N1
Host-JHOST=…demo site

All parameters can be overridden on the command line with no changes to the .jmx file.

🔵 Smoke Profile

-Jthreads=1 -Jloops=1
Single user, single pass — sanity check that the endpoint is alive.

🟠 Baseline Profile

-Jthreads=5 -Jloops=10 -Jramp_up=10
5 users, 10 iterations each — establishes normal-traffic benchmarks.

🔴 Stress Profile

-Jthreads=50 -Jloops=20 -Jramp_up=60
50 concurrent users — finds performance limits and breaking points.

📊 Key Metrics — What We Measure

Metric What It Means Target (Green) Warning Critical
Avg Response Time Mean time to receive a full response < 2,000 ms 2–4 s > 4 s
P90 Response Time 90% of requests finish within this time < 3,000 ms 3–5 s > 5 s
P99 Response Time Worst-case — only 1% of users are slower < 5,000 ms 5–8 s > 8 s
Throughput Requests handled per second Higher = Better — Drops under load
Error Rate % of HTTP 4xx/5xx responses 0% < 1% > 1%
Latency Time until first byte received from server < 500 ms 500ms–1s > 1 s
Why P90 over Average? Averages are skewed by fast responses. P90 tells you what 90% of real users actually experience — a much more honest measure.

🚀 How to Run — Step by Step

  • 1
    One-time setup — download JMeter
    npm run perf:setup  # Downloads Apache JMeter 5.6.3 (~60 MB)
  • 2
    Run the login performance test (default: 1 user, 1 loop)
    npm run perf:login
  • 3
    Run with custom load (e.g. 10 users, 5 loops, 30s ramp-up)
    bash jmeter/scripts/run.sh login -Jthreads=10 -Jloops=5 -Jramp_up=30
  • 4
    Open the HTML dashboard in your browser
    npm run perf:report:login
  • 5
    Regenerate PDF from existing results
    npm run perf:pdf

🔄 CI/CD — GitHub Actions Pipeline

Triggers

🌙 Nightly Schedule

Runs automatically every day at 01:00 UTC — continuous performance baseline monitoring.

🖱️ Manual Trigger

GitHub Actions UI → Run workflow — pick threads, loops, ramp-up from dropdowns.

🔗 Workflow Call

Other workflows can call this one — e.g. trigger performance tests automatically after smoke tests pass.

What CI Does

  • 1
    Sets up Java 17, Node 20, and downloads JMeter (cached)
  • 2
    Installs Playwright Chromium for PDF generation
  • 3
    Runs the JMeter test plan with configured parameters
  • 4
    Uploads PDF + HTML + JTL as 30-day artifacts
  • 5
    Posts avg/max response time + error rate to job summary
  • 6
    Sends email report (if MAIL_* secrets set)
  • 7
    Posts Slack notification with pass/fail status + link

🔔 Notifications & Integrations

📧 Email Report

After each CI run, a PDF report is sent via SMTP to the configured recipient. The email includes:


• Run summary (plan, users, loops)
• Avg + Max response time
• Error rate
• Link to GitHub Actions run
• PDF attached

💬 Slack Notification

A Slack message is posted to the configured channel with:


• Pass ✅ or Fail ❌ status
• Plan name + virtual user count
• Branch name
• Direct link to the GitHub Actions run
• Response time metrics

Configuration: Both integrations are optional and activated by setting GitHub repository secrets: MAIL_HOST, MAIL_USER, MAIL_PASS, MAIL_TO for email | SLACK_WEBHOOK_URL for Slack. No code changes required — just add the secrets in GitHub → Settings → Secrets.
